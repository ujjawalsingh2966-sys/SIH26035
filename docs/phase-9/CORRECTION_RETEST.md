# Phase 9: Correction and Retest Lifecycle

## 1. Overview
Not all observations generated by Technicians initially pass peer-review verification. Reviewers possess the capability to bounce examinations back natively with comments describing exactly what requires remedy.

## 2. Process
1. Reviewer determines test parameter observations (e.g. Tare or Eccentricity testing) were conducted improperly.
2. Reviewer calls `POST /:id/workflow/return` with a `reason`.
3. The system captures the reason into the `reviewNotes` of the Test Case.
4. Status transitions to `RETURNED_FOR_CORRECTION`.
5. The `AuditService` captures a `RETURN_FOR_CORRECTION` event encompassing the reason in the `metadata` record.

## 3. Retesting 
When a test transitions to `RETURNED_FOR_CORRECTION`:
- Locks are relaxed. The Technician can modify parameters and re-enter observations.
- The Technician must manually advance the state back into `TESTING` before entering new observation records for security purposes.
- Once fixed, the test flows again into `READY_FOR_REVIEW`.
